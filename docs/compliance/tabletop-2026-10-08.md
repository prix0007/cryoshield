# Tabletop exercise: malicious bundle served from cryoshield.app

> `add-privacy-and-compliance` task 7.5; spec `privacy-compliance` "Breach and incident response", scenario "Tabletop
> exercise". Run on paper on 2026-10-08 by the security-reviewer agent against the current runbooks:
> [`incident-runbook.md`](incident-runbook.md), [`docs/deploy.md`](../deploy.md) ("Releasing to production",
> "Rollback", "Rotating the Fly tokens") and `.github/scripts/deploy/rollback.sh`. Nothing was executed; no command
> was run against Fly, GitHub, Pimlico or DNS. CryoShield is an open-source project; there is no company.

## Scenario

A leaked Fly deploy token is used to run `fly deploy --image <attacker image>` on `cryoshield-web`. The image is the
real site with one change: `/app/` sends the PRF output of every unlock to an attacker's server. Because the change
also adds that server to the CSP it serves, the browser allows the request. The image serves a copied `release.json`
naming the real live commit. Production is on OP Sepolia; the dev site is not touched.

Alternative entry points considered at the end: an owner GitHub account takeover (a malicious `v*` release) and a
DNS/registrar takeover.

## Alternative entry points

- **Owner GitHub account takeover.** The attacker can publish a `v*` release and deploy through the real pipeline, so
  the image matches a run. Detection then relies on the release list (`gh release list`) and the owner's security log.
  Containment is the same; cutting off the attacker also means GitHub session and key revocation. The tag ruleset and
  environments do not help against the owner's own account: hardware-key 2FA on the owner account is the control
  (already a mainnet re-gate item in `deploy.md`).
- **DNS or registrar takeover.** Rollback cannot fix DNS (`deploy.md` → Rollback). The runbook's step 2 collects DNS
  history, but nothing in the repository records the expected registrar lock, CAA and DNSSEC state to compare against.
  **Gap G5.**
- **Dev site compromise** (`cryoshield-web-dev.fly.dev`): a different RP ID, so it cannot use production credentials
  or open production vaults. SEV2. Covered.

## Gaps found

| ID | Gap | Fixed here? | Proposed issue title (for the maintainer to file) |
|---|---|---|---|
| G1 | The runbook trusted `release.json`, which the suspect image serves | **Yes**: `incident-runbook.md` §3.2 now lines up `fly releases` with `deploy.yml` runs by time | n/a |
| G2 | Users cannot verify which bundle they loaded (review F7) | No | "Publish each release's tree hash in the GitHub Release and on /architecture" |
| G3 | While production is scaled to 0 there is no notice at the domain | No | "Prepare an incident-notice image that can be deployed in place of the site" (needs an OpenSpec change) |
| G4 | No written procedure to pause gas sponsorship | No | "Document pausing and resuming sponsorship in apps/web/docs/paymaster-policy.md" |
| G5 | Expected registrar lock, CAA and DNSSEC state is not recorded | No | "Record the expected DNS and registrar security state in docs/deploy.md and check it in the six-monthly review" |
| G6 | One person can release, roll back and rotate secrets (bus factor) | No (accepted for the testnet) | "Name a backup maintainer before mainnet" |

The gaps are listed as proposed issues rather than filed, because filing is the maintainer's call. None blocks the
testnet; G2–G5 should be closed or explicitly accepted at the `mainnet-gate` review.
