CryoShield system map

How a secret goes from your browser to permanent storage and back, which pieces we run, and how code reaches production.

This page mirrors docs/system-design.md in the open-source repository.

Components and trust boundaries

CryoShield runs exactly one thing: a static website on Fly. Everything else is either on your device or third-party infrastructure that never sees a plaintext secret.

From one key tap to your secret

Each tap returns one 32-byte PRF output for a fixed salt. Two separate keys are derived from it: one is public (the lookup), one never leaves memory (the wrap key).

What each flow touches

Create a vault

  1. Tap key 1, then key 2. Each creates a discoverable credential and returns its PRF output; their P-256 public keys become smart-account owners.
  2. The browser picks a random vaultId, encrypts the secret and wraps the data key once per key.
  3. One more tap signs the userOp. Pimlico sponsors it and EntryPoint calls createVault.
  4. The same blob is uploaded to Arweave with CryoShield-Vault-Id and CryoShield-Locator tags.

Unlock or recover

  1. Tap any enrolled key once. The PRF output gives the locator and, after the lookup, the wrap key.
  2. resolveLocator over public RPCs returns candidate vaultIds. No account and no gas needed.
  3. Each candidate is tried; only the genuine vault authenticates, so clones and junk are skipped.
  4. The recovery CLI does the same over USB, falls back to Arweave, and checks copies against the latest on-chain event hash.

How code reaches cryoshield.app

Nothing reaches main or production without a spec, a pull request and a green ci-ok. There is no bypass, including for admins.
